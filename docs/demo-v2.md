# 三分钟演示

使用两个独立浏览器会话分别登录客服、审核员，避免切换身份时丢失当前页面。

**0:00–0:30：业务问题**

“这是一套模拟电商售后系统。订单里有耳机和收纳包，只有耳机坏了；Agent 需要明确退款对象，不能直接退整单。”

**0:30–1:15：调查和证据**

提交订单 CF000001 的耳机左耳无声诉求。展示订单、售后历史 MCP 工具结果，以及中文政策来源。解释模型决定查询顺序；资格、金额和权限由代码检查。看到方案 199 元，收纳包 50 元不包含在退款中。

**1:15–2:00：审批和执行**

审核员核实证据及排除条款后批准；客服再确认执行。展示工单和业务账本。解释审批绑定方案版本，金额或商品变化不能沿用旧审批。

**2:00–2:40：失败恢复与防重**

查看进程终止恢复测试的实测记录：独立业务服务已提交，而 worker 尚未收到响应时被终止；重启后按原执行 ID 查询结果，退款和工单各一条。再说明不同案件重复申请也会被业务权益唯一键阻止。

**2:40–3:00：效果与边界**

打开[本轮完整评测报告](../eval/reports/v2/IMPROVEMENT.md)，说明模型、样本规模、失败案例和费用。区分工程测试、完整集、已看过失败后的回归、多轮验收与历史30条子集；不能将有限合成集或成功演示说成系统普遍100%成功。

另一个演示：CF000002 查询真实延误轨迹，按政策发10元模拟券。无需审核员批准，但必须由客服确认；重复领取被阻止。

已处理的演示权益不能再次领取。需要再次演示时使用新的同类订单，例如 CF000004、CF000007（退款）或 CF000005、CF000008（物流）。初始化命令不会清空历史记录。

本地本轮验收已经使用了 CF000016 退款和 CF000011 补偿。后续可选择未消费的
CF000019（退款）和 CF000014（补偿），演示前先在工具结果中核对已有售后权益。
当前演示显式使用 DeepSeek；Qwen 服务保持停止，不占用共享3090。

两个可讲清的失败与改进：用户夹带“跳过审核”时仍处理合法退款但保留审核；
用户要求退款却不符合条件时解释拒绝，不能自行换成物流补偿方案。
提示词负责指导调查，最终审批和执行限制仍由业务代码执行。
